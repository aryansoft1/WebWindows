# WebWindows Admin Trusted State-Change Contract v1

Phase 2E.1 freezes the request authority required to mutate WebWindows administration state. It does not enable the Production Capability Broker or alter ReviewDecision, PublishedRelease, Catalog binding, Runtime identity, Native Bridge, or Public API authority.

## Current authentication and session model

SystemManager authenticates the literal `admin` account against `webwindows_users` through Classic ASP Session. A successful login stores the user identity and an admin marker, with a 120-minute session timeout. Phase 2E.1 adds a separately random admin-authority marker and a session-bound CSRF token. Existing sessions without the authority marker are not accepted as authenticated Admin sessions and must log in again.

The token is generated by trusted MySQL `RANDOM_BYTES(32)`, encoded as 64 lowercase hexadecimal characters, and stored only in server Session. There is no predictable or weak fallback. The login captcha response bootstraps a pre-authentication token; successful login rotates both the authority marker and CSRF token. Logout clears identity and security state and abandons the Session. Multiple pages or tabs in the same valid Session share the stable token; requests do not rotate it.

Classic ASP does not expose a portable application-level Session ID regeneration API. Rotating the CSRF token and authority marker invalidates pre-login proofs, but does not by itself prove that the underlying `ASPSESSIONID*` cannot be fixed or replayed. Production must verify IIS configuration for cookieless-session disablement, Session cookie regeneration/fixation behavior, and cookie attributes. This is deployment evidence, not an application contract inferred by the repository.

## Eligible mutation request

A mutation is eligible only when every condition is true:

1. It is an explicitly inventoried `POST` request.
2. Its media type is `application/x-www-form-urlencoded`.
3. `X-WebWindows-Admin-Request` matches the endpoint family.
4. The authenticated Classic ASP Session contains the admin identity and random authority marker (login uses the pre-auth Session instead).
5. `X-WebWindows-CSRF` exactly and timing-independently matches the server Session token.
6. `Origin`, when present, exactly equals `https://www.y0.hk`; otherwise Referer is parsed and its scheme, host, and port must reconstruct that exact origin.
7. `Sec-Fetch-Site`, when present, equals `same-origin`.

Missing Origin and Referer fail closed. Suffix, substring, wildcard, `null`, malformed, cross-site, query token, text/plain, multipart, and GET mutation attempts fail closed. Stable errors include `CSRF_REQUIRED`, `CSRF_INVALID`, `ADMIN_ORIGIN_INVALID`, `ADMIN_FETCH_CONTEXT_INVALID`, `ADMIN_CONTENT_TYPE_REQUIRED`, and `ADMIN_MUTATION_POST_REQUIRED`. Responses and IIS audit fields never include supplied or expected tokens, cookies, or Session IDs.

The authoritative machine-readable inventory is `data/security/admin-state-change-v1.json`. It includes developer approval and suspension/API-key revocation, ReviewDecision approval/rejection/re-review and approved permission selection, release publication, delist/revoke events, Catalog administration, user administration, and data-center administration. The UI references `deleteUser.asp`, but that endpoint is absent from the repository; Phase 2E.1 does not invent a new deletion behavior.

## Audit and trust composition

The shared gate appends compact IIS log fields for action/target, result category, authorized user ID, CSRF category, and origin category. The timestamp and HTTP result remain standard IIS log fields. Values are bounded and never contain tokens. Endpoint success adds the target identity where available.

CSRF eligibility does not override any platform authority. ValidationReport binding, immutable ReviewDecision, permission subset selection, PublishedRelease uniqueness, exact package identity, release events, and Catalog projection constraints continue to run after the CSRF gate. Concurrent tabs share the CSRF token; existing database transactions and immutable constraints, not CSRF, decide concurrent approve/reject/publish/revoke outcomes.

## Browser and UI boundary

SystemManager pages use `SystemManager/assets/js/admin-security.js` to keep the token in a closure and add it only to same-origin mutation requests. The authenticated trust-management pages no longer execute the previous remote Tailwind/Lucide scripts. Obvious user and data-center table HTML injection sinks were replaced with DOM nodes and `textContent`.

`web.config` sets `Content-Security-Policy: frame-ancestors 'self'`, `X-Frame-Options: SAMEORIGIN`, and a same-origin Referrer Policy for SystemManager. This preserves the actual same-origin SystemManager shell iframe while denying attacker-origin embedding. CSRF does not defend a trusted-origin XSS; package content must remain sandboxed and must never execute unsandboxed on the Admin origin.

## Deployment verification still required

- Confirm production uses only canonical `https://www.y0.hk` for SystemManager mutation traffic, including reverse-proxy forwarded behavior.
- Confirm MySQL supports `RANDOM_BYTES(32)` and fails closed if unavailable.
- Confirm IIS forwards Origin, Referer, Sec-Fetch-Site, Content-Type, and `X-WebWindows-CSRF` without rewriting or logging token values.
- Confirm the actual `ASPSESSIONID*` cookie is `Secure`, `HttpOnly`, host-only with a narrow Path where deployable, and `SameSite=Lax` or stricter without breaking login/navigation.
- Confirm cookieless sessions are disabled and exercise session-fixation behavior on the production IIS version.
- Confirm the SystemManager response headers are present after hosting-panel/IIS configuration inheritance.
- Verify the login-page MD5 dependency's pinned version and SHA-384 SRI in production. It does not receive the authenticated post-login token; local vendoring remains preferable for a later deployment-only hardening change.

## Browser acceptance status

The in-app browser could render the two-origin local fixture, but its security client blocked the local Session/JSON endpoint with `ERR_BLOCKED_BY_CLIENT` and did not expose page request primitives. No full browser pass is claimed from that environment. The committed fixture remains available for a normal browser, while the repository tests exercise the same-origin, malicious suffix, strict Referer, cross-site Fetch Metadata, missing/wrong/other/old Session token, multi-tab, logout replay, method, Content-Type, and immutable trust-gate decisions. End-to-end login/review/publish on real Classic ASP/IIS remains a mandatory production verification item.

Production Browser/IIS/MySQL/HTTPS evidence remains incomplete. `productionCapabilityBrokerV1` remains `false`.
